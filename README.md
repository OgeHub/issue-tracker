# Issue Tracker API

A REST API for registering users, authenticating them with JSON Web Tokens (JWT),
and creating and managing issues. The API is built with FastAPI, SQLAlchemy, and
Pydantic. User passwords are hashed with Argon2 through `pwdlib`; Alembic manages
database schema migrations.

## Features

- Register users with a unique email address and validated password.
- Log in with email and password. A successful login sets an HTTP-only
  `access_token` cookie containing a signed JWT.
- Create, list, retrieve, and update issues.
- Associate every issue with its author and restrict issue updates to that
  author.
- List users and retrieve a user by UUID.
- Paginate issue and user lists with `page` and `limit` query parameters.
- Validate request and response data using Pydantic schemas.
- View the interactive API documentation generated by FastAPI.

## Technology

- Python 3.14 or newer
- [uv](https://docs.astral.sh/uv/) for project and dependency management
- FastAPI with its standard extras
- SQLAlchemy ORM
- SQLite (the current database engine configuration)
- Alembic
- `pwdlib[argon2]` for password hashing
- PyJWT for access tokens
- Pydantic Settings for environment-based configuration

## Create and set up a project with uv

These commands show the initial setup workflow for a new project. Replace
`name_of_app` with the project directory/name you want. Run commands from that
project directory after initialization.

### Initialize the project and add dependencies

```console
uv init name_of_app
cd name_of_app
uv add "fastapi[standard]"
uv add sqlalchemy
uv add "pwdlib[argon2]"
uv add alembic
uv add pyjwt
uv add pydantic-settings
```

`fastapi[standard]` includes the FastAPI command-line tooling and Uvicorn used
to run the development server.

### Initialize and apply database migrations

Initialize Alembic once in a newly created project. Before generating a
revision, configure Alembic to import the application's SQLAlchemy metadata
(see this repository's `alembic/env.py` for the pattern), and define the user
and issue models.

```console
uv run alembic init alembic
uv run alembic revision --autogenerate -m "create users and issues tables"
uv run alembic upgrade head
```

Review every autogenerated revision before applying it. In this repository,
the Alembic environment and initial users/issues migration are already present;
do not run `alembic init` again. To apply the checked-in migrations to the
configured database, run:

```console
uv run alembic upgrade head
```

When models change, create a new revision with an appropriate message, inspect
the generated migration, and then upgrade:

```console
uv run alembic revision --autogenerate -m "describe the schema change"
uv run alembic upgrade head
```

## Configuration

Create a `.env` file in the project root. The application requires all three
settings below:

```dotenv
JWT_SECRET_KEY=replace-with-a-generated-secret
JWT_EXPIRATION_MINUTES=30
DATABASE_URL=sqlite:///./issues.db
```

Generate a cryptographically strong secret and copy its output into
`JWT_SECRET_KEY`:

```console
uv run python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Keep `.env` private and do not commit real credentials or secret keys. The
repository ignores `.env` by default. The current database engine is configured
for SQLite; `DATABASE_URL` must therefore use a SQLite URL unless the engine
configuration is updated for another database backend.

## Run locally

From the project root, install/synchronize the locked dependencies, apply
migrations, and start the development server.

Recommended (uses the project's FastAPI entrypoint via uv tooling):

```console
uv sync

uv run fastapi dev
```

Alternative (explicit Uvicorn invocation):

```console
uv sync

uv run uvicorn issue_tracker:app --app-dir src --reload
```

## API overview

All resource routes are under `/api`. Successful resource responses use a
`message` and `data` envelope. User and issue identifiers are UUIDs.

| Method | Path | Authentication | Description |
| --- | --- | --- | --- |
| `GET` | `/` | No | Welcome message |
| `POST` | `/api/auth/register` | No | Register a user |
| `POST` | `/api/auth/login` | No | Log in and set the `access_token` cookie |
| `GET` | `/api/users/` | Yes | List users; accepts `page` and `limit` |
| `GET` | `/api/users/{user_id}` | Yes | Retrieve a user by UUID |
| `POST` | `/api/issues/` | Yes | Create an issue for the authenticated user |
| `GET` | `/api/issues/` | Yes | List issues; accepts `page` and `limit` |
| `GET` | `/api/issues/{issue_id}` | Yes | Retrieve an issue by UUID |
| `PATCH` | `/api/issues/{issue_id}` | Yes | Update an issue owned by the authenticated user |

### User registration

`POST /api/auth/register` accepts:

```json
{
  "first_name": "Ada",
  "last_name": "Lovelace",
  "email": "ada@example.com",
  "photo": null,
  "password": "ExamplePass1!"
}
```

The password must be at least 8 characters and contain an uppercase letter, a
lowercase letter, a digit, and a special character. Duplicate email addresses
are rejected. Password hashes are stored; the plaintext password is not
included in user responses.

### Login and authentication

`POST /api/auth/login` accepts an email and password:

```json
{
  "email": "ada@example.com",
  "password": "ExamplePass1!"
}
```

On success, the API sets an HTTP-only `access_token` cookie. Subsequent
authenticated requests must send that cookie. The token uses the HS256 signing
algorithm and expires after the configured `JWT_EXPIRATION_MINUTES`. The
current login cookie is configured with a 30-minute maximum age, `SameSite=Lax`,
and `Secure=False`; configure secure cookie settings and explicit trusted CORS
origins before deploying behind HTTPS in production.

### Issues

An issue has a title, description, status, priority, UUID, and author (`user_id`).
The title is limited to 100 characters. A missing description is stored as an
empty string. New issues default to status `open` and priority `medium`.

Allowed status values:

- `open`
- `in_progress`
- `closed`

Allowed priority values:

- `low`
- `medium`
- `high`
- `critical`

Issue updates accept any subset of `title`, `description`, `status`, and
`priority`. Only the issue's author can update it; retrieving and listing issues
requires authentication, but the current implementation does not filter issue
lists or individual issue retrieval by owner.
